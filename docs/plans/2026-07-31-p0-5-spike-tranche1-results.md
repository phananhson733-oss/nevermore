# P0-5 Spike · Tranche 1 结果

日期：2026-07-31
对应规范：`docs/plans/2026-07-31-public-tools-p0-1-p0-3-p0-5-spec.md` §7.9
状态：**第一批（2 站深测 + 10 站可达性）已完成。结论：机制不成立，需重新设计后再谈上线。**

## 零、方法与替换项（必须先读）

本批**未使用生产 DataForSEO 凭据**。理由：那套凭据（Railway 项目 `signalframe` / production / worker）服务付费客户分析链路，正是规范 §8.3 警告的"顺手复用"风险。

| 环节 | 规范设计 | 本批实际 | 对结论的影响 |
|---|---|---|---|
| 爬取 | `PUBLIC_TOOL_CONTEXT_CRAWL_BUDGET`（40 页/深度 3/60s） | **完全一致**，用仓库真实 guarded crawler（SSRF guard + DNS pinning + robots + sitemap + BFS） | 无 |
| 提炼 + 发散 | `OPENAI_MODEL` | **Claude 替代** | 结论偏**乐观**：更强的模型只会让候选质量更高 |
| 搜索量校验 | DataForSEO `keyword_overview` | **Ahrefs `keywords-explorer-overview`** | 口径与团队 333 词实测同源；抽样验证 `internal link audit`=700/KD5、`orphan pages seo`=450，与既有文档完全一致 |
| 候选上限 | ≤150/站 | 100/站 | 结论偏**乐观**：尾部候选质量更差，放到 150 通过率只会更低 |

**因此下面所有通过率都应视为上限，不是期望值。**

### 1.2 按 discoveryBasis 拆分（**本 spike 最重要的一条**）

> 补测说明：Tranche 1 首轮把依据文档的第 2 步（AI 提炼卖点）和第 3 步（基于卖点发散）合成了一步做，也没给候选打 `discoveryBasis` 标签 —— 这违背了 `2026-07-29-gengrowth-p0四工具-输入输出与实现流程总结.md` 四、P0-5 的处理过程（该文档明确把两步都标为"核心，新增"，并要求输出每条带"发现依据"标签）。首轮的 linear.app 候选里因此混入了大量来自品类先验知识的词（`jira alternative`、`linear vs jira`），抬高了通过率。
>
> 补测做法：显式产出第 2 步的卖点清单（**只用爬到的内容**），再严格只从卖点发散，每站 40 个纯 `site_proposition` 候选。

| discoveryBasis | linear.app | astrologywiki | 合计 | 通过项最高搜索量 |
|---|---:|---:|---:|---:|
| `traditional_expansion` | 51%（70→36） | 73%（60→44） | **62%**（130→80） | 28,000 |
| `site_proposition` | **15%**（40→6） | **7.5%**（40→3） | **11%**（80→9） | **200** |

**产品文档 2026-07-30 把核心机制从"对比竞品内容缺口"改成"从产品卖点 AI 发散"，理由是前者天花板低。实测结果是：新机制的通过率只有它所取代的传统扩展路径的约 1/6，且产出的最高搜索量只有 200。**

这不是调参问题，是机制内部的逻辑冲突：依据文档第 3 步要找的是"**这个产品的独特角度，还没人系统性地在内容里覆盖过**"，第 5 步又要求"**必须过真实搜索量校验**"。一个角度没人覆盖，通常正是因为没人搜索它。**两个要求按构造互相对立。**

#### 1.2.1 但结论不是"砍掉卖点发散"——是验收指标设错了

通过校验的 `site_proposition` 候选虽少，质量却明显不同：

| 站点 | 通过的卖点候选 | 量 / KD |
|---|---|---|
| linear.app | `slack helpdesk` | 200 / KD21 |
| | `slack to jira ticket` | 90 / **KD3** |
| | `agentic coding tool` | 90 / — |
| astrologywiki | `archetypal astrology` | 60 / **KD0** |
| | `jungian astrology` | 20 / **KD1** |

对照传统扩展路径产出的高量词的可赢性：

| 候选词 | 量 | KD |
|---|---:|---:|
| rising sign calculator | 28,000 | **65** |
| moon sign calculator | 25,000 | **60** |
| natal chart calculator | 20,000 | **76** |
| zodiac calculator | 5,800 | **78** |
| free birth chart calculator | 4,200 | **76** |

**对一个 DR=0 的站点，传统路径产出的是一堆漂亮但打不动的数字；卖点发散产出的是少量 KD 0–3、真正可能拿下的角度。** 这与团队自己在选词文档中反复验证的结论一致——跟大品牌拼同一个品类名，新进入者结构性打不过。

因此错的是 §7.9 的验收门槛（"至少 10–15 个有搜索量的词"）：**它奖励传统扩展、惩罚差异化发散**，与产品定位相反。门槛应改为「量 × 可赢性」口径，例如「至少 N 个 `volume > 0` 且 `KD ≤ 站点可达阈值` 且未被现有页面覆盖的候选」。

**最终产出（astrologywiki，8 个）**

|---:|---:|---|

这 8 个是**真的**：都有真实搜索量、SERP 里都已有低 DR 站突破、且都不是站点已有页面在覆盖的词。

但对照 §7.9 的门槛（"至少 10–15 个"）：**astrologywiki 现在不通过（8 < 10）**，linear.app 惨败。

#### 两条量化结论

1. **单次运行的净产出率约 5.7%。** 要凑够 10–15 个真实机会，需要 **175–260 个候选**，而规范 §7.1 的上限是 150 —— 上限设低了，且提高上限会同比抬高 LLM 与数据源成本。
2. **产出质量由客户所处品类决定，不由工具决定。** 消费内容品类 8 个，B2B SaaS 品类 2 个（且其一是品牌词 `linear vs jira`）。而 GenGrowth 的 ICP 明确是"欧美 B2B/B2C 客户"—— **对其中的 B2B 客户，这个工具按当前设计几乎交付不了东西。**

### 1.5 关于「DR → KD 上限」：建议不要用 KD 做主闸门

Owner 要求按 DR 映射 KD 上限。校准数据说明 **KD 是错的仪器**：

**实测基准**：`astrologywiki.com` DR = **4.0**，`gengrowth.ai` DR = **0.0**。astrologywiki 有 39+ 个优化良好的计算器页面，但在美国**只有 2 个词进前 20**：

| 词 | 量 | KD | 位置 |
|---|---:|---:|---:|
| kai cenat zodiac sign | 70 | **0** | 9 |
| elliot page zodiac | 20 | 12 | **11** |

即：DR 4 的站，只有 KD 0 能进前 10，KD 12 卡在第 11 位。若据此定「DR 0–5 → KD ≤ 5」，会把下面这些词全部误杀：

| 词 | 量 | KD | 但前 10 里存在 DR ≤ 10 的站 |
|---|---:|---:|---|
| rising sign calculator | 28,000 | 65 | ✅ |
| astro chart calculator | 1,000 | 77 | ✅ |
| big three calculator | 1,400 | 63 | ✅ |

原因：**KD 估的是前 10 的平均强度；「有没有弱站突破过」是另一回事。** 一个 KD 65 的词，如果 SERP 里已经站着一个 DR 5 的站，说明这个 SERP 是可穿透的。

**建议的判据（按优先级）**

1. **主闸门 —— SERP 直接证据**：Ahrefs `keywords-explorer-overview` 的 `serp_domain_rating_top10_min` 过滤字段（注意：只能用于 `where`，不能 `select`）。判据 `serp_domain_rating_top10_min ≤ 站点 DR + 6`。对 DR 0–4 的站即 `≤ 10`。这是逐词的观测事实，不是模型估计，符合仓库的证据诚实性要求。
2. **站点自校准上限**：用 `site-explorer-organic-keywords` 读客户**自己已有排名**的 KD 分布，取其 top-10 排名词的 KD 上界作为"已证明能达到的天花板"。astrologywiki 即 KD 0（top-10）/ 12（top-20）。这是每站自适应的，比任何全局表都准。
3. **仅在冷启动时用 DR→KD 兜底**（新站、无任何排名、SERP 字段不可用）：

   | 站点 DR | KD 上限（保守兜底） |
   |---|---|
   | 0–5 | ≤ 5 |
   | 5–15 | ≤ 15 |
   | 15–30 | ≤ 25 |
   | 30–50 | ≤ 40 |
   | 50+ | ≤ 60 |

   > ⚠️ 这张表只有 DR 4 一个实测锚点（astrologywiki），其余档位是外推，**未经验证**。它只应作为前两条都不可用时的兜底，且 UI 必须标注为估计而非观测。落地页不得把它当作方法论公开，否则就是把未校准假设包装成权威。
4. DataForSEO 是否有等价于 `serp_domain_rating_top10_min` 的字段**尚未确认** —— 若没有，规范 §7.5 的数据源选型需要重新评估。

## 二、可达性：30% 的站点根本拿不到上下文

尝试 10 个站，7 个成功。

| 站点 | 结果 | 原因 |
|---|---|---|
| ridge.com | ✗ | 403 Cloudflare "Attention Required!" —— bot 防护 |
| www.personio.com | ✗ | 429 "Vercel Security Checkpoint" —— bot 防护 |
| www.factorialhr.com | ✗ | `https://www.` → 301 → **`http://`**，SSRF guard 正确拒绝协议降级（站点自身配置问题） |

前两个是真实的产品阻塞：**P0-5 的第一步就会在受 bot 防护的站点上失败**，而这类站点在 DTC 电商和欧洲 SaaS 里占比不低。落地页必须诚实写出这个限制，且失败态要能解释原因，不能只报"扫描失败"。

第三个是我们的安全策略正确工作，但用户视角仍是"你的工具打不开我的网站"，同样需要可理解的错误文案。

> 排查过程中另有一条自查记录：初次运行时 astrologywiki.com 返回 0 页，**是 spike 脚本的 bug**（直接调 `crawlSite`，漏了生产 `crawlPublicSitePreview` 的 apex→www 入口重定向解析），不是产品缺陷。修正后拿到 39 页。

## 三、机制层面的三个问题

### 3.1 爬到的不是产品页，是博客

7 个站共 223 个 200 页面：

| 类型 | 页数 | 占比 |
|---|---:|---:|
| 产品 / 定价 / 功能 | 21 | **9%** |
| 博客 / 案例 / 变更日志 | 53 | 24% |
| 其他 | 149 | 67% |

最极端的是 **linear.app：10 个页面里 0 个产品页，8 个博客**。爬虫在 24 MiB 字节预算内就停了（`stop=max_total_bytes`），根本没走到 `/pricing`、`/features`、`/customers`。mercury.com 也一样：38 页里 31 页是博客。

这不是调参问题。从 origin 做 BFS 必然一头扎进博客归档（那里链接最密、层级最浅），而 P0-5 第 2 步要的恰恰是"产品卖点 / 差异化 / 目标人群"。**输入错了，后面每一步都在放大错误。**

规范 §7.4 已经标注"没有定义如何给队列做页面价值排序"—— 本批证明这不是待优化项，是**阻塞项**。

### 3.2 强制搜索量校验会杀掉 GEO 定位

规范 §7.2 第 3 步明确要"既有传统 Google 式短词，也有人会问 ChatGPT/Perplexity 的自然语言问法，呼应 GEO 定位"；第 5 步又要求所有候选**必须**过真实搜索量校验。

这两条互相矛盾：问句通过率 33%（B2B 场景 17%），而问句正是 GEO 的载体。**用 SEO 的闸门去筛 GEO 的产出，会把 GenGrowth 最想讲的差异化直接筛没。**

补充一条机制事实（实测）：Ahrefs 对库里没有的词**静默不返回**，不区分"搜索量 = 0"和"无数据"。200 个候选里 84 个（42%）属于这类。若照规范 §7.2 写的"零搜索量直接丢弃"实现，就会把"无数据"当成"零搜索量"—— 这违反仓库 `unavailable ≠ 0` 的硬约束。DataForSEO 是否有同样行为需单独确认。

### 3.3 过了搜索量闸门 ≠ 是机会

astrologywiki.com 的 62 个"通过校验"候选里，**约 65% 是站点已有页面正在覆盖的词**（词元重叠 ≥80% 的粗略判据，个别匹配偏松，但方向明确）。按搜索量排前 8 名的全部已有专属页面：

| 搜索量 | 候选词 | 站点已有页面 |
|---:|---|---|
| 28,000 | rising sign calculator | `/en/big-three-calculator` |
| 25,000 | moon sign calculator | `/en/big-three-calculator` |
| 20,000 | natal chart calculator | `/en/birth-chart-calculator` |
| 13,000 | saturn return calculator | `/en/saturn-return-calculator` |
| 5,800 | natal chart free | 首页 |
| 4,200 | free birth chart calculator | 首页 |
| 3,200 | sun moon rising calculator | `/en/big-three-calculator` |

**工具把站点已有的页面又推荐了一遍，并称之为"机会地图"。** 对付费用户这是可信度杀手。

真正未覆盖且有量的只剩 **22 个**，其中最好的几个（`when is my saturn return` 5,300、`saturn return meaning` 2,900、`what is a stellium in astrology` 1,600）确实是合理的内容机会 —— 说明机制并非毫无价值，但**必须加一个"已覆盖过滤"阶段**。

### 3.4 而"已覆盖过滤"本身依赖 3.1

linear.app 的同一检查只显示 7% 已覆盖 —— 这是**假象**：爬虫压根没拿到它的产品页，所以过滤器无从判断。

于是两个问题相乘：爬取拿不到产品页 → 覆盖过滤失效 → 工具会把客户**已经在排名的词**当作新机会推荐。这比单纯的低通过率更糟。

## 四、成本与时延

| 项 | 实测 |
|---|---|
| 爬取墙钟（40 页预算） | 1.6s ~ 32s，中位约 12s |
| 爬取停止原因 | 4/7 站 `max_urls`，2/7 站 `max_total_bytes`（24 MiB 先于 40 页耗尽） |
| Ahrefs 校验 | 21–33 units/行，本批共 **2,689 units**（配额 100,000/月，已用 3,274→5,963） |
| 单站 100 候选校验成本 | 约 1,300 units ≈ 月配额的 1.3% |
| DataForSEO | **本批未消耗**，单价仍未实测 |
| LLM | 本批用 Claude 替代，未产生 `OPENAI_API_KEY` 成本，**生产 token 成本仍未实测** |

按 Ahrefs Lite 100,000 units/月推算，纯校验环节约可支撑 **每月 75 次运行**（100 候选/次）。这个量级对一个公开免登录工具**远远不够** —— 需要重新核算数据源档位，或大幅收窄单次候选数。

## 五、对 §7.9 上线门槛的判定

规范门槛：*"至少 10–15 个非重复、相关、跨多个意图的验证词"*。

| 站点 | 结果 | 判定 |
|---|---|---|
| astrologywiki.com | 22 个有量且未覆盖 | **形式上通过** |
| linear.app | 无法判定（爬取未拿到产品页，覆盖过滤失真） | **无法判定** |

**但这个门槛本身设错了。** 它只衡量"还剩几个词"，没有衡量"这些词是不是真的机会"。astrologywiki 形式上通过，靠的是它处在一个搜索需求极其成熟的消费品类 —— 在那种品类里你说出任何东西都有量，AI 发散没有创造价值，只是把页面标题读了一遍。而在 B2B SaaS（linear）这种品类里，通过率腰斩，问句几乎全灭。

**结论：不建议按当前设计进入 Phase 4。**

## 六、建议的设计修改（在重跑 spike 前先定）

0. **先改验收指标，再谈其他**（§1.2.1 / §1.4 / §1.5）。门槛改为三段式：`volume > 0` **且** `serp_domain_rating_top10_min ≤ 站点 DR + 6`（**不是** KD 阈值，理由见 §1.5）**且** 未被现有页面覆盖。同时按实测净产出率 5.7% 重定门槛数量与候选上限：要 10–15 个真实机会需要 175–260 个候选，现规范上限 150 偏低。
   > 连带：`site_proposition` 与 `traditional_expansion` 的产出**必须在 UI 上分开展示并各自计数**（依据文档已要求每条带"发现依据"标签）。混在一张表里，高量低可赢性的传统词会淹没少量高可赢性的卖点词。

1. **爬取必须做页面价值排序**，不能纯 BFS。优先 sitemap 中的 `/pricing`、`/features`、`/product`、`/solutions`、`/use-cases` 与首页；显式降权 `/blog`、`/news`、`/customers`、`/careers`、`/legal`。这是 3.1 的直接修复，也是 3.4 的前提。
2. **拆成两条产出线，不共用一个闸门**：
   - **SEO 线**：传统短词 → 强制搜索量校验（保留现设计）
   - **GEO 线**：自然语言问句 → **不走搜索量校验**，改用"是否被 AI 答案引擎引用/是否有 SERP question 特性"这类信号，或明确标注为"无搜索量数据的假设性角度"
   否则 §7.2 第 3 步和第 5 步互相抵消。
3. **漏斗必须加第 5 阶段"已被现有页面覆盖"**，并在 UI 上把"已覆盖"和"未覆盖"分开展示。`M` 不是最终产出，`M − 已覆盖` 才是。
4. **`unavailable ≠ 0` 必须在校验层显式实现**：数据源不返回 ≠ 搜索量为零，两者要分开计数、分开展示。
5. **失败态文案**：bot 防护（403/429）与协议降级要各自有可理解的解释，不能统一报"扫描失败"。
6. **重新核算数据源档位**：当前 Ahrefs Lite 配额只够约 75 次运行/月。要么换档位，要么把单次候选上限从 150 大幅下调。
