日期：2026-08-10
标定数据：Phase 0 spike（20 词，$0.157）+ Tranche 2 机制重跑（20 站 / 1,522 候选 / 255 SERP，$1.1715）
凭据：Railway `signalframe` worker 生产 DataForSEO 账号（Owner 授权测试用）
状态：**单价已实测拟合，可作为免费层额度与月预算的定档依据**

## 一、DataForSEO 单价（实测拟合，非报价单推算）

| 端点 | 计费形状（拟合自实测） | 拟合校验 |
|---|---|---|
| `dataforseo_labs/google/keyword_overview/live` | `$0.01205 + $0.00012 × 返回行数` | 175 行→$0.0330（实测 0.0330）；174 行→$0.0329（实测 0.0329）；33 行→$0.0160（实测 0.0160） |
| `serp/google/organic/live/advanced` | `$0.002 / 词`（固定） | 255 次调用总计 $0.5100 |
| `backlinks/bulk_ranks/live` | `$0.0240 + $0.0000323 × 目标数` | 17 目标→$0.0246（实测）；~1,200 目标 2 次调用→$0.0869（实测） |
| `dataforseo_labs/google/ranked_keywords/live` | `$0.0329 / 站` | 15 次调用总计 $0.4927 —— **产品链路已弃用，见下** |

> **计费按「返回行」而非「请求词」**，这是本模型最重要的一条：`keyword_overview` 对库里没有的词静默不返回（实测请求 1,522 词只回 382 行，返回率 25%），而这些没返回的词**不计费**。所以「一次校验 150 个候选」的真实账单只按其中约 38 个有数据的算。

## 二、单次运行成本（产品参数：150 候选 / ≤20 SERP 抽样 / 单市场）

| 环节 | 调用 | 成本 |
|---|---|---|
| 搜索量+KD+intent 校验 | `keyword_overview` × 1（150 词合批，约 38 行返回） | **$0.017** |
| 可赢性证据：抽样 page one | `serp/organic/advanced` × 20 | **$0.040** |
| 可赢性证据：域名权威解析 | `bulk_ranks` × 1（≤200 个去重域名） | **$0.031** |
| 本站覆盖判定 | Google Search Console API | **$0** |
| **合计（DFS）** | | **≈ $0.088 / 次** |

**区间**：SERP 抽样是唯一的可调项。抽 10 词 → $0.068；抽 30 词 → $0.108。取整对外口径 **$0.09/次，上下不超过 $0.11**。

### 为什么覆盖判定是 0 成本

Owner 2026-08-10 拍板 P0-5 走 Google 登录 + GSC 授权。既然拿得到用户自己的 Search Console 查询数据，「这个词站点是不是已经在服务」就该用用户自己的精确数据判断，而不是花 $0.0329 去 DFS 查第三方推断的已排名词。这一条决策把单次成本从 $0.121 降到 $0.088（**降 27%**），而且判据更准——GSC 是 exact query 的实测曝光与加权位置，DFS ranked_keywords 是抽样推断。

## 四、LLM 成本（口径分开，不并入 DFS 账）

Tranche 2 实测（15 站，gpt-5.6-luna，两步分离：卖点提炼 + 双泳道发散）：

| 项 | 15 站合计 | 单次运行 |
|---|---|---|
| 输入 token | 748,086 | **≈ 49,900** |
| 输出 token | 30,807 | **≈ 2,050** |
| 调用次数 | 30 | 2 |

输入占比高是因为要把 14 页正文摘要喂进去。**单价取决于最终部署的模型与渠道**，本轮走 codex/ChatGPT 配额未产生 API 计费，故不写死金额；产品化前需按选定模型回填。降本手段是现成的：正文摘要已截断到每页 1,300 字符，可再压；两次调用不可省（两步分离是 Tranche 1 补测确立的机制前提）。

> ⚠️ 连带待办：Railway worker 的 `OPENAI_MODEL` 仍钉在 `gpt-4o-mini`，与 Owner 指示的现役 5.6 系列不符，产品化前需更新部署配置。

## 五、非计费成本（但要计入容量规划）

| 项 | 实测 |
|---|---|
| context 爬取 | ≤14 页 / ≤60s，中位 12s；自有带宽，不计费 |
| DFS 链路延迟 | overview 2.6–9.1s + SERP p50 4.5s/p90 9.5s（并发 5）+ bulk_ranks 1.4s，合计 **<30s** |
| 整体墙钟瓶颈 | LLM 发散，不是 DFS |
| 爬取失败率 | 20 站中 5 站被 bot 防护挡（25%）——这些运行**不产生任何 DFS 成本**，在第一段就终止 |

25% 的失败率反而是省钱项：失败发生在 context 阶段，第二段的付费调用根本不会触发。

## 六、成本护栏（实现时必须带）

1. `maxProviderCostUsd` 单次硬顶（建议 $0.25，是 p50 的 3 倍），超限即停并返回 `partial`。
2. 账户级日预算断路器，触顶降级为 503 `keyword_source_unavailable`，**绝不输出未校验候选词**。
3. 候选数硬上限 150、SERP 抽样硬上限 20——两者都是成本的线性放大器。
4. DFS 凭据与付费产品 worker 隔离：共享账号会让 P0-5 的流量把 40203（account cost limit exceeded）连坐到付费客户的分析链路上。本轮 spike 共花 $1.33 无所谓，持续消耗必须分账。
5. 每次响应解析 `cost` 字段并累加上报——这是唯一的成本可观测性来源。
